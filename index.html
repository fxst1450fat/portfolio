CASE 01

週次 売上分析レポート

課題 — BEFORE

社長が出張などで店に入れない期間、売れ筋商品の欠品に気づけるのはベテランスタッフだけでした。気づかないまま機会損失が発生していました。

やったこと — SOLUTION

  • APIを持たないPOSシステムから、AutoHotkey で毎朝6時に販売データを自動抽出
  • rclone で店舗の Google ドライブへ自動転送
  • Claude で店舗別・商品別に分析し、問題点を抽出
  • PowerPoint / Excel で、社長がそのまま読める形に出力

成果 — RESULT

これまで見えなかった 死に筋商品・欠品リスク商品・機会損失商品 が数字で見える状態に。
社長が現場にいなくても、早め早めに手を打てるようになりました。

CASE 03

在庫切れ 機会損失アラート

課題 — BEFORE

週次レポートだけでは、日々発生する欠品を防ぎきれませんでした。気づいたときには在庫切れが起きていました。

やったこと — SOLUTION

毎朝9時に、社長とスタッフのLINEへ自動でアラートが届く仕組みを構築しました。

POSシステム（CSV / Shift-JIS） ↓ 毎朝エクスポート Google ドライブ（Drive API で参照） ↓ 時刻トリガー実行 Google Apps Script ├ csvParser.gs … Shift-JIS対応のCSV解析 ├ main.gs … 残り日数の算出と緊急度判定 ├ lineNotify.gs … 通知文の整形と送信 └ config.gs … PropertiesService による秘匿情報管理 ↓ 緊急度別に通知を整形 LINE Messaging API → 社長・担当スタッフのLINE

判定ロジック — LOGIC

残り日数 ＝ 在庫数 ÷ 日次販売数
緊急度条件アクション
緊急1.5日以下即発注対象
注意3.0日以下早期発注推奨
注視7.0日以下在庫推移を監視
安全7日超通常運用

ベテランの勘に頼っていた発注判断を、数式と4段階のルールに落とし込みました。

成果 — RESULT

導入から1ヶ月時点で、社長の体感として 在庫切れの発生が約50%減少。 ※ 導入1ヶ月時点の定性評価です。今後、数値での効果測定を予定しています。

TROUBLE SHOOTING

原因究明と、再発防止の仕組み化

事象 — PROBLEM

新規導入した設備で、稼働中の不具合が 1日あたり10件 発生。調整による対応では解消せず、稼働の妨げとなっていました。

原因究明と対策 — SOLUTION

  • 調査を重ね、特定部品の緩みが原因ではないかと仮説を設定
  • 日本から部品を手配し、交換を実施

成果 — RESULT

不具合発生を 1日10件 → 0件 に解消。

歯止め — PREVENTION

直して終わりにせず、定期交換の手順を文書化。現場がメンテナンスを継続できる仕組みとして落とし込み、対策が一過性で終わらない状態にしました。

ベテランの経験を、誰でも実行できる手順に変える。
在庫アラートで発注判断を数式と4段階のルールに落とし込んだのも、まったく同じ考え方です。

※ 各改善施策の効果（稼働率・不良率・工数）については、当時の測定記録が手元に残っていないため、数値としての記載を控えています。上記の件数・人数・期間は、すべて実数です。
